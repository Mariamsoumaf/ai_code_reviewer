# AI Code Reviewer (Final Project – Software Construction)

A Python tool that reviews code written by AI assistants and finds
**security vulnerabilities** and **copy-pasted (duplicated) code**
before the code is used.

Designed with *Clean Code* (Robert C. Martin), Chapters 5–10.

## 1. Problem
AI coding assistants write code fast, but the code is often **unsafe**
and **repetitive**:
- Pearce et al. (*"Asleep at the Keyboard?"*, IEEE S&P 2022): out of 1,689
  programs generated by GitHub Copilot in security-relevant scenarios,
  about **40%** were vulnerable.
- GitClear (*AI Copilot Code Quality*, 2025): copy-pasted code blocks are
  rising while refactoring is falling. *(Industry report from a company
  that sells code analytics.)*

Developers often accept this code without a careful review.

## 2. Research question
> Does AI-generated Python code contain security problems and duplicated
> code, and can a static-analysis tool detect them automatically before
> the code is used?

## 3. Methodology
**Static analysis**: the tool reads the code and its syntax tree
(`ast`) **without running it**, then applies a set of independent rules.

1. Read the file and build the syntax tree (`SourceFile`).
2. Run each detector (`SecurityDetector`, `DuplicateDetector`).
3. Sort findings by severity (HIGH → MEDIUM → LOW) and print a report.

## 4. Techniques (what the tool finds)

| Rule | Example of unsafe code | Severity | Safer alternative |
|---|---|---|---|
| Code execution | `eval(text)`, `exec(text)` | HIGH | parse the input explicitly |
| Hard-coded secret | `DB_PASSWORD = "admin123"` | HIGH | environment variable |
| SQL injection | `"SELECT ... " + name`, f-string, `.format()` | HIGH | `?` placeholders |
| Shell injection | `shell=True`, `os.system(...)` | HIGH | list of arguments |
| Unsafe deserialization | `pickle.load(file)` | MEDIUM | `json` |
| Weak password hash | `hashlib.md5`, `hashlib.sha1` | MEDIUM | `hashlib.pbkdf2_hmac` + salt |
| Duplicated code | same 5+ lines in two places | LOW | one shared function |

## 5. Why this methodology?
- **Safe:** the reviewed code is never executed, so dangerous code cannot
  harm the machine.
- **Fast and offline:** no AI model, no internet, no extra libraries.
- **Explainable:** every finding shows the line, the reason and a safer
  alternative, so the developer learns while fixing.
- **Extensible:** a new vulnerability = one new rule class.

## 6. Clean Code Chapters 5–10 in the design

| Chapter | Where it is applied |
|---|---|
| 5. Formatting | PEP 8 (checked with `pycodestyle`: 0 errors); public methods first, private helpers below them (newspaper order) |
| 6. Objects and Data Structures | `Finding` and `CodeLine` are pure data structures (frozen dataclasses). `SourceFile` and the detectors are objects that hide their data and expose behavior |
| 7. Error Handling | Custom exceptions (`SourceFileNotFoundError`, `NotAPythonFileError`, `InvalidPythonSourceError`) instead of error codes; detectors return an empty list, never `None`; `main.py` turns errors into a clear message |
| 8. Boundaries | `SourceFile` is the only class that touches the file system and `ast.parse`. Learning tests (`tests/test_ast_learning.py`) document how `ast` behaves |
| 9. Unit Tests | 39 tests with `unittest`, one concept per test, readable names, fast (≈0.01 s), independent (F.I.R.S.T.). Every rule is tested with unsafe **and** safe code |
| 10. Classes | Small classes with one responsibility (SRP). Each security rule is its own class; rules that only check a function name share the `ForbiddenCallRule` parent (no repeated code). Adding a rule changes no existing class (Open/Closed). `CodeReviewer` depends on the `Detector` abstraction, so tests can pass a fake detector |

## 7. How to run
```bash
python main.py examples/ai_generated_login.py   # 10 issues (6 high, 3 medium, 1 low)
python main.py examples/safe_login.py           # no issues (same features, fixed)
python -m unittest -v                           # run the 39 tests
```
Exit codes: `0` no issues, `1` issues found, `2` file could not be read
(useful in a CI pipeline). Requires Python 3.9+. No extra packages.

## 8. Results
| File | High | Medium | Low | Total |
|---|---|---|---|---|
| `ai_generated_login.py` (typical AI-style code) | 6 | 3 | 1 | 10 |
| `safe_login.py` (after fixing every finding) | 0 | 0 | 0 | 0 |

## 9. Limitations
- Rule-based: it finds known patterns only, not every possible vulnerability.
- Duplicate detection compares lines exactly; copies with renamed variables
  are not found.
- It detects problems but does not fix them; the developer decides the fix.

## Project structure
```
ai_code_reviewer/
├── main.py                        ← command line entry point
├── reviewer/
│   ├── source_file.py             ← boundary: file system + ast
│   ├── finding.py                 ← Finding + Severity (data structures)
│   ├── exceptions.py              ← custom errors
│   ├── code_reviewer.py           ← runs detectors, sorts findings
│   ├── report_formatter.py        ← builds the text report
│   └── detectors/
│       ├── detector.py            ← abstract base class
│       ├── security_detector.py   ← runs all security rules
│       ├── security_rules.py      ← one class per vulnerability
│       └── duplicate_detector.py  ← copy-paste detection
├── examples/
│   ├── ai_generated_login.py
│   └── safe_login.py
└── tests/                         ← 39 unit tests
```
